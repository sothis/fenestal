Fenestal development setup

How a change gets from the source tree to a verdict: one build script, thirteen trees, six ways to run the result, and a ledger that says what was run where. Drawn from the files in the working tree on 13 October 2026, not from the documentation. The last section lists where the two disagreed, and what has been put right since.

The whole loop

What is being built

The library is layered so that the core names no window server and no graphics API. Everything crossing that line goes through one of two dispatch tables.

A consumer links fenestal plus the runtime of the platform it chose: Vulkan, m, threads and wayland-client or core xcb on Linux; Vulkan, user32 and gdi32 on Windows. FreeType, glslangValidator and wayland-scanner are run during the build and never linked.

Thirteen trees

Every tree is build/<target>/<variant>. A bare ./build.sh sweeps them in the order of this table, row by row, and stops at the first failure. That order matters because later trees borrow generated files from earlier ones.

What a variant adds

releasenothing; Release, LTO, -march=native
asanDebug, -fsanitize=address,undefined
tsanDebug, -fsanitize=thread
analyzer-fanalyzer, with no build type set, so it is an optimised tree
gcDebug, section-per-function and --gc-sections

Checker trees turn -march=native off. mingw-w64 ships no sanitizer runtimes, which is why the cross target refuses two variants.

The build tools link FreeType and run during the build, so a cross build cannot bake a font: it would compile mkfont for Windows and then fail to run it. The loan is FNL_GENERATED_DIR for the cross tree and FNL_FONT_DIR between trees of one native target, the second taken only when the lender's atlas is newer than everything it is made from. The cross loan is held to the same test, and since the cross tree cannot bake its own, build.sh refuses a stale one and names the command that makes a fresh one.

Where a round runs

Twelve seconds a cell, CPU over six of them. The four desktop environments hold the display's 60, give or take two, at every rate. schenker falls to 48 to 53 from 45 resizes a second upward, and aspire dips to 54 at 30. Set against the README's latest laptop sweep (the table after the reaper went in), every cell is within seven frames a second, and the afternoon's sweep of the same day was within four: 46 to 50 there for schenker from 45 upward, and 53 for aspire at 30. The README puts what is left under 60 down to the driver's swapchain create, one a frame, and most of the gap between the two machines to schenker's panel at 125%.

A hand on the border

border61 · 11.7%59 · 16.8%60 · 18.3%16 · 118.9%48 · 37.2%20 · 118.7%59 · 32.8%

Every row of a sweep is the caller asking for sizes; this one is the window server's own resize, which on Win32 is the manager's loop from the press to the release. The window rests three seconds before the press. Pressed in its first second, the same window on schenker's NVIDIA device used to run at 93 fps on a 60 Hz panel for the whole drag: the loop had no display period until its sixtieth present and never learnt one under a run of rebuilds. It now borrows one from four early samples that agree (ba0e261), and the same drag is 50 fps. On the Intel devices a hand is about fifteen sizes a second, with the swapchain create at 43 to 47 ms and more than a core busy. Native Wayland has no cell: the harness cannot aim at its edges.

A second monitor at another rate

schenker's external monitor was put at 50 Hz beside the panel's 60, and at 30 for two cells. The round held on both devices, started on the panel and moved across and started on the monitor: 66 four times. The two devices are held to different clocks. NVIDIA's present waits for the monitor the window is on, 50 fps and then 30. Intel's waits for the panel whichever monitor that is, 60 fps on the monitor at 50 Hz and again at 30, so a window there draws frames the monitor has no refresh for. Both outputs are the Intel device's, so the hybrid copy to an NVIDIA output could not be tried.

What the cross-check found

Two other models read the build side and the harness side independently, from the files alone, and their reports were compared with a third reading; a further model then checked this page against the files and its eight corrections are applied. Nothing in the documentation was flatly wrong. It had drifted in places, and a few safeguards are thinner than they sound.

Still open

Nothing about the setup. What is open is technical, and TODO.md has it:

  • sleep, battery, lidA timed sleep was tried from here on schenker and the laptop did not wake by itself, neither by the timer nor by wake-on-LAN, so what a window does across a suspend is still unknown. Wake timers were left allowed on mains there and want putting back. Running on battery, energy saver and the lid are untried.
  • Intel's extra framesWhat becomes of the frames the Intel device presents faster than a slower monitor refreshes: dropped, or shown late. Not looked at.
  • Intel's driver stallPrevented and not explained. It was caught again with the workaround taken out, on the HD 530: none of eighty starts whose first resize came a third of a second after the window opened, and the thirty-fifth of those whose first came after four seconds. Its stacks are kept in docs/intel-swapchain-stall-stacks.txt: the window's thread, inside the driver's hook, and one of the driver's own wait on the same lock, while the frame's thread waits in vkCreateSwapchainKHR. docs/intel-swapchain-stall.md is the draft report, still owed a second capture, a release build of Windows, a small reproduction and a newer driver tried.
  • hybrid copyUntested until an external output belongs to an NVIDIA device.

Known and left as it is: the skip for a guest whose screen is too small has been written and not seen. The last full round, stress.py, minimal.py, the two sanitizers on the native targets and a sweep, ran on the frame-loop change just before it was committed, so the ledger has those lines as dirty.

Settled: fixed in commit 7217546, or answered by a run

  • ledger never writtenNo ledger.jsonl existed. stress.py, minimal.py and pace.py have each been run over everything they cover, none failing, and status.py says never nowhere. The win10 guest was off for the first pass and was started for the rest.
  • layering uncheckedNothing ran tools/check-layering.py. build.sh now runs it after every build that succeeds, once for a sweep. The sweep of all thirteen trees ended with it, and the layering holds.
  • stale font, crossThe cross tree took the Wayland release bake if the directory existed. It is now held to the freshness test a native checker tree's lender passes. The sweep passed that test; the refusal itself has not been seen, since the bake was fresh.
  • laptop pacingBoth laptops present fewer than 60 frames at some resize rates. That is how the README last measured them, to within seven frames in every cell over two sweeps, so it is not a change.
  • in flightThe nine uncommitted files, a GPU as a dimension of a laptop round, were driven by every round above and then committed as 68717c8.
  • style tools unrunNeither clang tool was installed. Both are now, at 21.1.8, and each has had its first run, recorded in its own config file and in CLAUDE.md (78af854).
  • tidy findings unreadclang-tidy has now run over all three trees, the Win32 one included: 66 findings past Annex K's check, every one read at its site and none a defect. They are listed by kind in .clang-tidy, so a finding not there is new (d794b5c).
  • guest screen checkThe harness asked a guest for a large enough screen but measured the whole desktop, so two monitors of 1280x960 passed it and the round then failed two size checks. It measures the monitor the round opens on now, and a machine that will not change its mode is skipped with the reason. The README says what a windowed guest needs: auto-resize off, and its display set in the guest (a19f997). Both guests pass on it; the skip itself has not been seen.
  • no style baselineclang-format parses its file and would change some 3,900 lines in 62 of 64 sources, all of it deliberate alignment, as the file's header predicted. Settled by decision: it is a reference for new code and not a check that can pass.
  • a period soonerThe frame loop had no display period before its sixtieth present, so a border taken in a window's first second was unspaced for the whole drag where the driver blocks nowhere. The spacing now borrows the mean of four early samples that agree, and the settled window's first sample replaces it. Every environment passed on it, with the sanitizers on the two native targets.
  • display scaleAt 150% the default window opened larger than a 1080p panel, its corner off the screen. On Win32 the library now fits an opening window to its monitor's work area, and a round that finds no room takes the window in by its border first. The scale is set from here by tools/probe/scale.c, and the round passed at 100, 125, 150 and 175% on each device of both laptops; neither panel is offered 200%.
  • input methodFNL_NO_INPUT_METHOD=1 leaves Wayland's input method unbound, so a round can type through the library's own composer in a window: 50 checks, none failed. Nothing is done about the output wine on Wayland never updates, and the README says why.
  • hook scopeThe edit hook covered C, shader and CMake sources only. It now covers the scripts under tools/, build.sh and run_all.sh as well.

Put right in CLAUDE.md, commit 59775bf

  • cross loan is fixedbuild.sh lends the cross tree build/wayland-vulkan/release/generated by name, so an X11-only build does not satisfy it. The docs said "the host build"; they now name the tree and the sweep's order.
  • three, or sixThe docs spoke of "all three environments". environment.ALL has six, the portal and its token belong to the four on this desktop, and pace.py sweeps those four and the laptops.
  • analyzer is -O3The analyzer variant sets no build type and inherits Release, where "the checker trees' Debug still wins" read as if it were Debug.
  • wine clipboardThe skip was tied to wine 10.0. The code decides at run time, by looking for wl_data_device in the loaded winewayland.so, so a later wine turns the section on by itself.
  • undocumentedWhat a tree holds beyond fenestal-testbed, build/fenestal.zip and tools/mkdist.py, run_all.sh, tsan.supp, options_wayland.sh, FNL_DRIVE_LEDGER, the other directories under build/ and where the examples' shader headers land each have a line now. native_relay.py still has none.
